# Current creation facts in native execution

The CreationObserved native facade uses the approved Git snapshot and the
existing qualified A3 current-address reader. It stores no user or policy rows.
The reader is an operational facts adapter outside Core, independently bound to
its network, generation, coverage, source set, reference, profile and limits.
A read-only OPS can consume the global observer's births while owning no raw
producer lane; the two source sets need not match.

Current registry ownership and grants take precedence over old birth namespaces.
Approved `addressScopes` provide isolation labels. A scope alone supplies no
registered-runtime proof, read association or operational claim. Matching genuine
dynamic namespace and actual runtime code can qualify existing group claims;
they create no new groups, claims or execution rules. Dynamic runtime authority
requires the actual anchored code hash and length to match the original included
birth, with no conflicting runtime or inclusion fingerprint. Execution before
that birth, or at the same height on a different branch, cannot use it. A fresh
runtime from the current execution uses its lifecycle namespace, without gaining
operational claims from an old persisted birth. WALLET facts can provide
the original actor's plain association. FACTORY facts identify a namespace and
provide no wallet actor. An empty point result provides no public or unregistered
classification. Native org selection still requires the mapped current owner
and honors an explicit selected org.

Each operation uses a private copy of owner, qualification and association maps
bound to its original View and native engine. The original programs and group
masks stay immutable and the same evaluator produces the signed approval and
creation plan. Fresh, failed, empty and rolled-back creations inside that actual
execution retain the existing temporal namespace semantics.

The default operation bound is 20 seconds, clipped by an earlier parent deadline.
It also applies to direct library entrypoints. The cache permits at most 64
distinct dynamic address reads and 256 KiB of canonical candidate evidence in
total. These limits can be lowered. Repeated frames share point observations;
static registry and shared paths avoid unnecessary dynamic reads. Each point
read retains its original observer/reorg stamp; a mixed stamp is rejected.
These are application bounds, not a claim about every PostgreSQL wire message
or total process memory.

For a call, the actual synchronous Recorder append finishes before final source
checks. Every original A3 pass is rechecked, then the original selected client
samples chain ID and full hash-qualified genesis. If A3 was read, it also samples
the highest original observer head by numeric height on that same client. If
persisted dynamic runtime authority is actually consumed, the execution anchor
is sampled by number before evaluation and again at the final gate. The final
sample is shared with the observer-head sample when both identify the same
header. Static Git permissions retain the existing historical noncanonical
selector behavior. Dynamic authority requires a canonical execution anchor. The
original View and context are checked after all blocking work. Normal observer
progress is permitted while the original head remains canonical. The endpoint
is trusted and logically consistent; these samples do not make output delivery
atomic with a later reorg. Only bounded result/provenance data is retained across
Append, including the original absolute deadline and parent cancellation, not
the canceled acquisition child or full execution tree. Append remains genuinely
synchronous and holds its credit until completion; elapsed deadlines withhold
protected output.

For raw submission, capture and the atomic financial/origin/visibleTo/creation
intent transaction finish first, followed by receipt matching. Then all original
A3 rechecks precede full network and original-head probes, receipt time/price-age
validation and the same View/context, immediately before Guard enqueue or direct
broadcast. No node probe runs inside the SQL transaction. A prepared financial
or intent row may remain after a final denial, with no enqueue or broadcast.
Another request still performs fresh native/A3 qualification before reusing that
row. The availability hint for capture never grants permission.

A bound Guard Pair probes its private selected full network before Prepare and
again at the final gate. The original Pair, Prepared, evidence and selected client
pointer must match. A different facade client or credential cannot substitute.
This adds two initial node requests for the bound Pair. Final network validation
uses two requests, plus one numeric ancestor request when A3 was read. A dynamic
runtime execution adds one numeric anchor request before evaluation and at most
one distinct request at the final gate (four final requests maximum). Every
extra probe uses the original operation deadline. Existing
unbound profiles, approval formats, fingerprints and TTLs keep their behavior.
After a broadcast attempt the acknowledged or uncertain hash remains truthful;
a late delivery failure does not turn an actual effect into an unexecuted denial
or trigger a retry.

State and native consumers obtain CreationObserved scopes through the typed
`CreationObservedSource` accessor. The legacy `Source` accessor deliberately
returns an empty value for this profile and cannot supply its approved scopes.
