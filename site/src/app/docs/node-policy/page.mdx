# Reth policies and configuration revisions

In Reth policy mode, OPS authenticates users and checks their linked sender,
organization, RPC methods and compliance requirements. Reth checks the active
execution policy on every actual call and deployment. Contracts and signed
Ethereum transactions keep their existing format.

This mode uses the V2 policy protocol. Leave `OPS_APPROVAL_TARGETS` unset;
the V1 signed-approval protocol cannot be enabled alongside it. OPS refuses
to start when both are configured.

Leave `CROSS_ORG_AUTHORIZATION_ORACLE_MODE` at `disabled`. The oracle answers
from OPS's own access rules, not from the node's execution policies, so OPS
refuses to start when it is enabled in this mode.

## Author and approve configuration

Open **Administration → RBAC → Configuration** and select an organization.
The execution-policy tab opens the execution-rules stream automatically in
Reth mode. Sign in with a named account; an operator or bootstrap token cannot
author or approve a revision.

| Stream | Contents |
| --- | --- |
| Groups | Group definitions, administrative roles, RPC methods and claims |
| Contracts | Registered contracts, ABI, read grants and event visibility |
| Execution rules | Groups, callable functions, argument conditions and nested calls |
| Compliance | Organization settings, thresholds and token configuration |
| Approvers | Eligible approval groups and trusted external CI identities |
| Platform | Shared infrastructure with code pins, tenant defaults and the price feed |

Start from the current source, edit it, and save a draft. Review the complete
changes and compiled policy before activation. A different human administrator
with current approval authority must activate it. Read-only administrators and
service principals can prepare ordinary drafts and reviews. Approver trust and
platform documents require a human author and a separate human approver.

An execution-rules revision remains one organization document containing all of
its group bindings. Review includes a compiled artifact for each bound group;
one approval activates the complete set together. Removing a binding removes
that group's execution rules. A caller needs an allowing rule in at least one
of their current groups; nested calls are checked separately.

Deploy the updated OPS and Reth versions together before activating grouped
revisions; older nodes reject the new feed.
Previously approved organization-wide artifacts remain valid until replaced.

Cross-stream dependencies are pinned by digest. Supply sibling revision IDs to
review and activate a related bundle together, such as an ABI and its execution
rules. Editing the selected bundle invalidates its review. Stale base revisions
must be reloaded and reviewed again.

Include each managed resource to keep, or explicitly list its deletion. Omitting
a managed resource is an error. Automation-created resources are retained as
drift for adoption in a later revision. Once a stream is active, its former
configuration mutation endpoints close. User onboarding, memberships, bans,
address links, sanctions and disclosure remain operational actions. Upstream
RPC credentials can still be rotated separately, or declared in the groups document as an environment variable name (`rpcCredential.fromEnv`) that activation resolves; the value never enters the document.

## Current limits

**Compiled size: 24,576 bytes (24 KiB) per group.** Each group's execution rules
compile into a separate policy program. The limit applies to that compiled
program, not the source document's length. Other groups' rules do not consume
its allowance, but many functions or complex rules within one group can still
exceed it. OPS rejects an oversized group before approval; it does not
automatically split the group. Simplify its rules and submit again. These
programs run privately inside Reth and are not deployed as public contracts.

**Execution budget: 100,000 policy gas per application call or deployment.**
All of the caller's groups evaluated for that call share this budget. If it
runs out before an allowing group is reached, execution is denied even when a
later group would allow it. Adding memberships can therefore make a previously
allowed operation fail. Raising the transaction's gas limit does not increase
the policy budget. Nested calls receive their own policy checks.

There is no universal supported rule count or membership count: cost depends on
rule complexity and how many groups must be checked before finding an allowance.
In one measured workload, an allowance in the last checked group succeeded with
11 memberships and exhausted the budget at 12. An early allowance succeeded
with 60 memberships. These measurements are examples, not guaranteed limits;
successful activation of a 60-group organization does not establish that every
caller can evaluate all 60 groups. Test representative rules and memberships
before rollout, and simplify expensive rules or remove unnecessary memberships
when the budget is exceeded.

**Compilation deadline: five minutes for the complete group set.** If any group
fails to compile or the deadline expires, OPS rejects the submission without
storing a partial compiled set. Keep the existing active revision while
simplifying the proposed rules and resubmitting.

## Preview and observe execution

An execution revision offers a node preview using `eth_call`, `eth_estimateGas`
or `debug_traceCall`. Use one of your linked addresses as `from`. The preview uses
current chain state and current facts; the active policy must permit execution.
A successful preview does not guarantee inclusion after state or permissions change.

Unapproved record getters can reveal information through their verdict, so
ordinary candidate previews cannot perform live record reads. A full human
organization administrator can select the audited diagnostic option to evaluate
these candidates. Diagnostic execution remains restricted to the selected
organization, including nested getters and account reads.

Activation commits a revision in OPS. The publication panel separately reports
whether Reth has applied the current facts. Requests fail closed while required
facts are unavailable or stale. Revocation applies to the next candidate built
after the new version reaches the node.

Use `GET /api/v1/me/transactions/{hash}/execution` with the original submitting
principal's JWT to follow a submitted transaction. Inclusion remains provisional
until the node reports finality. OPS then registers successful CREATE/CREATE2
results and commits visibility bookkeeping. Wait for `reconciled: true` before
depending on automatic deployment registration. A missing receipt, a policy
denial or an expired identity does not prove that an already-running candidate
cannot be included. While a transaction is pending, OPS keeps it deliverable
itself (see [Renewal and recovery](#renewal-and-recovery)); the sender does not
need to resend it after a node restart.

## Shared signers and service principals

Several OPS principals may link the same Ethereum address. Their permissions
remain separate: each transaction and simulation is bound to its authenticated
principal as well as its signer. Sharing a signing key does not share status
visibility or combine memberships. Review this binding choice when enabling the
new mode, particularly if an automation service shares a key with a human.

Agents can use Azure service-principal login, refresh tokens, scoped context,
revision APIs, operational APIs and RPC directly. The configuration context
also reports the API's capabilities (streams, human-only streams, approval
modes, document size limit, and whether the pinned policy compiler is available
on this deployment), so a headless client can discover what it may do before
drafting. Human approval is a separate
authenticated action. Trusted CI activation requires an externally signed proof
bound to the exact revision bundle and configured reviewers; possessing a service
JWT alone does not permit activation. MCP tooling is not required.

## Operator configuration

The deployment's read privacy profile still applies in Reth policy mode.
Under `PRIVACY_READ_PROFILE=strict`, sends containing `visibleTo` are refused,
diagnostic reads as another user are unavailable, and diagnostic traces expose
only the permission verdict. Ordinary traces use `callTracer` and hide nested
values the caller could not read through storage access. State and block
overrides remain unsupported.

Group documents accept supported RPC methods and configured aliases. Adding
an unfiltered passthrough method requires named platform-authorized authors
and approvers; organization administrators may retain or remove existing grants.

Set `OPS_NODE_POLICY_MODE=reth` and point `NODE_URL` at the guarded Reth node.
Configure the private policy endpoint with `OPS_NODE_POLICY_URL`,
`OPS_NODE_POLICY_TOKEN`, `OPS_NODE_POLICY_PRIVATE_KEY_FILE`,
`OPS_NODE_POLICY_KEY_ID`, `OPS_NODE_POLICY_CHAIN_ID` and
`OPS_NODE_POLICY_DEPLOYMENT_ID`. The signing-key file contains a base64 Ed25519
seed or private key. Configure the corresponding public key and matching network
identity in the Reth launcher. Keep its private endpoint off user-facing networks.

Reth mode also needs the execution-tracking database
(`EXECUTION_DATABASE_URL`, `EXECUTION_ADMIN_DATABASE_URL`; see
[Configuration](/docs/configuration#execution-tracking-database-reth-mode)).
In production it belongs on its own PostgreSQL instance.

The default fact lifetime is 30 seconds, publication interval one second,
simulation identity lifetime one minute (`OPS_NODE_POLICY_IDENTITY_TTL`) and
transaction identity lifetime five minutes
(`OPS_NODE_POLICY_TRANSACTION_IDENTITY_TTL`, 120 to 600 seconds). OPS publishes a fact change as soon as it
commits; the publication interval is the heartbeat that renews the facts'
lifetime and the fallback while change notifications are interrupted. Only
changes to what the node enforces start a publication: memberships and their
expiry, linked addresses, bans and KYC, groups and their claims, contract
ownership and grants, shared infrastructure, preregistered addresses, sanctions
and active execution policies. Edits to names, notes or metadata do not.

OPS keeps its connections to the private endpoint open and splits them into
three bounded pools, so a burst of transactions never delays fact
publication:

| Variable | Default | Carries |
| --- | --- | --- |
| `OPS_NODE_POLICY_CONTROL_CONNS` | 4 | fact publication and node status |
| `OPS_NODE_POLICY_TRANSACTION_CONNS` | 64 | transaction submission and simulation |
| `OPS_NODE_POLICY_RECOVERY_CONNS` | 16 | transaction outcome checks and renewals |

Each accepts 1 to 1024. Requests beyond a pool's size wait for one of its
connections. The guarded Reth node's private listener accepts at most 128
connections by default; keep the sum of all three pools across every OPS
instance within it (84 per instance at the defaults). When the node also runs
its separate control listener (`OPS_NODE_POLICY_CONTROL_LISTEN` on the node),
set `OPS_NODE_POLICY_CONTROL_URL` to it: fact publication and readiness checks
then use that listener, and only the transaction and recovery pools count
against the main listener's limit.

OPS checks the node's readiness in the background every second and, on every
instance, right after each publication, not once per request. Every request
requires the facts current in the database when it arrived, so a revocation
committed before a request always applies to it. When the node has not
applied those facts yet, a node that supports it waits for them (up to its
fact wait, one second by default) and only then refuses; OPS passes such
requests on for up to one second after it first sees the node behind, at most
16 at a time per instance (each waiting request holds a transaction
connection), and refuses the rest itself. A request refused because publication is
pending is answered with 503, `Retry-After: 1` and, for callers with verbose
errors, the reason `publication_pending`: retry it unchanged. A request is
also refused with 503 when the node does not answer a readiness check, when its
facts have expired, or when OPS has had no successful readiness answer for five
seconds. `GET /ready` follows the same rule, so a short publication does not
take every instance out of a load balancer at once.

OPS records which principal submitted each transaction before it sends the
transaction to the node, so another principal sharing the signing key cannot
take it over, even after a node restart: such a submission is refused with 409
and one generic message, before any compliance step runs. Concurrent
submissions share one database commit. A submission the node refuses because
publication is pending (above) leaves nothing behind: resend the same signed
transaction. A transaction already final is answered with its hash and not
sent again.

Once OPS has recorded a submission, an error answer does not mean it was
refused:

| Answer | Meaning | What to do |
|---|---|---|
| 503, `Retry-After: 1`, reason `publication_pending` | Nothing was kept | Resend the same signed transaction |
| 503, `Retry-After: 1`, "the transaction may still execute" | Recorded; delivery to the node failed | Check its status, or resend it unchanged (idempotent) |
| 503, `Retry-After: 1`, reason `pending_limit` | Nothing was kept: the deployment's pending transactions are at the pending-work limit | Resend it unchanged after the delay |
| 429, `Retry-After: 1`, reason `principal_pending_limit` | Nothing was kept: your own pending transactions are at the per-principal limit | Resend it once some of your transactions are included |
| 429, `Retry-After: 1`, reason `org_pending_limit` | Nothing was kept: your organization's pending transactions are at the per-organization limit | Resend it once some of your organization's transactions are included |

A transaction refused for one of these limits has already passed the
compliance check: resend the same signed transaction, which reuses its
travel-rule record; a newly signed transaction needs a record of its own.
| 409, "nonce is already used or held by another pending transaction" | The node's pool refused its nonce. OPS stops renewing it; it can still settle if the competing transaction disappears | Check its status; replace it at the same nonce if needed |
| 409, "conflicts with an earlier submission" | The signed transaction is bound to another submission | Do not retry |

The owner can follow a transaction at `GET /api/v1/me/transactions/{hash}/execution`:

| Status | Meaning | Final |
|---|---|---|
| `pending` | Submitted; waiting for inclusion. OPS keeps it deliverable | no |
| `provisional` | Included in a block that is not finalized yet; it can still return to `pending` after a reorganization | no |
| `renewal_stopped` | OPS will not renew it (see the reason), but it may still settle: it can still be included while its last identity is valid, and is then reported as included | no |
| `included` | Executed in a finalized block | yes |
| `reverted` | Reverted in a finalized block | yes |
| `dropped` | Can never execute: a finalized transaction used its nonce (reason `nonce_consumed`) | yes |

A `renewal_stopped` transaction carries one reason: `max_age` (pending longer
than `OPS_NODE_POLICY_MAX_AGE`), `principal_banned`, `kyc_missing`,
`not_member`, `organization_deleted`, `principal_deleted`,
`method_not_allowed`, `sender_unlinked`, `visible_to_not_allowed`,
`compliance_denied` (a re-check refused it), `nonce_conflict` /
`replaced_in_pool` (the node's pool refused its nonce), or `node_rejected` (the
node kept refusing a renewed identity). Resending the same
signed transaction as the same principal is a new submission with every check.
OPS reports `dropped` only once a finalized block has used the transaction's
nonce and the transaction itself was never included; an expired identity alone
never makes a transaction final.

Final statuses are kept for `RETENTION_NODE_SUBMISSIONS` (7 days by default)
and then the lookup answers 404. Ownership of deployed contracts and
`visibleTo` rules are applied once a transaction is final, exactly once. A
created address another organization already owns is not registered again;
the status then carries the note `effects_not_applied`. Every finalization is
recorded in the access log as `ops.system.finalized` on behalf of the principal
before it takes effect, and a refused effect as `ops.system.effects_refused`.

When several OPS instances share one database, exactly one of them publishes
facts and reconciles submissions at a time. Each instance campaigns for a
database lease (a session-level advisory lock); the others stand by and take
over within one publication interval once the holder's database session ends.
A clean stop or a process crash ends the session at once. A host that vanishes
mid-session keeps the lock until Postgres notices the dead connection; the lease
session sets its own TCP keepalives, so that takes about ten seconds and the
next instance takes over before the facts expire. At the default lifetime only
an outage longer than the lifetime stops execution, and then it stops rather
than running stale; a lifetime under about fifteen seconds leaves no room for
that takeover.
The lease needs a direct database connection or a session-pooling proxy;
transaction pooling (PgBouncer in transaction mode) breaks session-level
advisory locks and would leave the lease orphaned. Change notifications
(PostgreSQL `LISTEN`/`NOTIFY`) need the same; without them OPS still publishes,
but only at the publication interval. With a pooler on another
host the database's keepalives only reach the pooler, so give the pooler client
keepalives of a similar bound, or a vanished OPS host holds the lease until the
pooler notices on its own. Keep
`OPS_NODE_POLICY_CONSUMER_ID` identical across instances — it names the node's
acknowledgement cursor, not the instance — or leave it at its default. Configure named platform operators through
`PLATFORM_ADMIN_SUBJECTS`. Supply the pinned Solidity compiler through
`POLICY_SOLC` or the executable search path. `GET /ready` returns 503 until the
node has fresh matching facts and required capabilities.

The guarded Reth node reads its own settings in the Reth launcher; they share
the `OPS_NODE_POLICY_` prefix with OPS but are not OPS settings. Set
`OPS_NODE_POLICY_STATE_DIR` to a dedicated subdirectory on a local filesystem,
not a volume's root or a symlink: owned by the node's user with mode 0700 and
empty when first used (the node creates it if its parent exists). One node
process locks it. A directory written by an older layout is refused; there is
no importer, so point the node at a new empty directory. Stop the node at a
finalized head before you switch: blocks above it would need their execution
evidence, which stays in the old directory. Allow about two small files per
policy fact change in the directory, besides each block's evidence: they stay
until a newer full snapshot replaces their chain and the blocks that use the
chain are past the manifest retention.

Size the node for the expected load:

| Variable | Meaning | Default |
| --- | --- | --- |
| `OPS_NODE_POLICY_CAPACITY` | Submissions and simulations the node tracks at once; more are refused | 262144 (about 370 MB when full) |
| `OPS_NODE_POLICY_EXPECTED_TPS` | Sustained transactions per second, at least 1 | 2000 |
| `OPS_NODE_POLICY_FINALITY_BOUND` | Seconds from inclusion until a block is final and written by the node: the larger of the deployed consensus's finality (finality depth × block time) and the node's write lag, at least 1 | 64 |
| `OPS_NODE_POLICY_PENDING_LIMIT` | Allowance for submissions still waiting for inclusion | 37500 |
| `OPS_NODE_POLICY_VERIFY_WORKERS` | Submissions and simulations admitted in parallel, 1–64 | 4 |
| `OPS_NODE_POLICY_MAX_CONNECTIONS` | Authenticated connections the private listener serves at once; above it fact publication and status are still served and other requests get 503 with `Retry-After: 1` | 128 |
| `OPS_NODE_POLICY_CONTROL_LISTEN` | Optional second private listener that serves only fact publication and status; recommended in production, on an interface only OPS can reach | unset |
| `OPS_NODE_POLICY_CONTROL_MAX_CONNECTIONS` | Connections the control listener serves at once | 16 |
| `OPS_NODE_POLICY_FACT_WAIT` | How long the node holds a request that needs newer facts than it has before it answers that facts are pending; `0s`–`5s` | 1s |
| `OPS_NODE_POLICY_MANIFEST_RETENTION` | How long the node keeps each finalized block's execution evidence after the block, `forever` (archive nodes) or a whole number of `s`, `m`, `h` or `d`, at least one hour | 7d |

Size `OPS_NODE_POLICY_MAX_CONNECTIONS` for every OPS instance that uses the
node: at least the sum of their connections to it. Private connections are
recycled after about a minute after a complete response; a request in flight
completes. A connection counts against the limit only once it has sent a
request with the node's token: a connection that sends no such request within
10 s, or a request with a wrong token, is closed. Run the control listener on a
separate interface that only OPS can reach (for example a firewalled private
network), so fact publication never shares a listener with other peers.

The retention of block execution evidence is a record-retention control: set it
from your documented retention policy. Evidence of blocks that are not yet
final is never removed, and `forever` keeps all canonical evidence.

A submission holds its slot until its block is final and written by the node,
or until its lease expires. The node reports a transaction as finalized only
once its block is final and written to disk, so a node crash never loses a
block OPS has treated as final. The node refuses to start when the capacity is below 1.25 ×
(transactions per second × (2 s + finality bound) + pending allowance).

Submissions the node tracks are not kept across a node restart. OPS sees the
restart and renews every transaction that is not yet included, with no client
action (see [Renewal and recovery](#renewal-and-recovery)). The node accepts the
renewed submission even when its transaction pool still holds the transaction,
as after a clean shutdown. Until then the node rejects status requests for the
transaction, and OPS keeps it pending and keeps polling. An unclean stop can
also lose the newest blocks the node had not yet written; their transactions
return to pending and OPS renews them the same way.

The guarded node refuses to start with a public RPC module that replays,
traces, validates or builds blocks (`debug`, `trace`, `ots`, `flashbots`, `mev`,
`testing`, or `all`), with `--rpc.forwarder`, with `--auth-ipc`, with
`--debug.reorg-frequency`, or with a `--db.sync-mode` other than `durable`.
Public methods that would re-execute blocks or build them answer error
`-32601`: `eth_callMany`, `eth_getBlockAccessList` and its `ByBlockHash`,
`ByBlockNumber` and `Raw` forms, `eth_simulateV1` and
`reth_getBlockExecutionOutcome`. The node also refuses to start if an enabled
public module would serve a method its release was not reviewed for. Use OPS's
signed simulations for calls, estimates and traces.

On the guarded Reth node, public `pending` block queries return no block, and
finalized history the node already holds re-executes without its policy
evidence; blocks it imports for the first time need the producer's execution
manifests.

The development stack uses Reth's local block production and an explicit short
finality depth. Its local finality behavior is for testing and does not establish
external consensus. Use the repository's `docs/implementation/ops-reth-stack.md`
for the isolated stack and acceptance commands. Keep node state and OPS databases
persistent across restarts.

## Renewal and recovery

A transaction identity lets the node execute a transaction only while it is
valid and only on the node process that received it: the node keeps pending
identities in memory, so a node restart forgets them. The elected OPS instance
runs a lease keeper that gives a pending transaction a new identity when the
node no longer holds it:

- it was recorded but never delivered (for example, OPS stopped between
  recording it and sending it, or the send failed);
- the node restarted (OPS sees a new node boot id), whether gracefully or after
  a crash;
- the node's pool lost it while its identity was still registered;
- its identity has at most half of its lifetime left while the transaction is
  still pending (congestion; see below).

A transaction that a reorganization returns to pending keeps its identity on
the node until finality and needs no renewal unless one of the above applies.

A transaction usually reaches a block within seconds, long before its identity
needs renewing, so in normal operation OPS renews almost nothing. Under
congestion an identity is renewed once at most half of its lifetime is left
(2.5 minutes at the default five-minute lifetime) and always before a quarter
of it is left. Renewals are spent within a budget
(`OPS_NODE_POLICY_RENEWAL_BUDGET` per second, 500 by default), earliest expiry
first; recovery after a node restart uses the same budget. Near the maximum
age, where a renewal could not extend the identity, OPS does not renew and
stops at the maximum age instead.

So that the budget can always renew what is pending in time, OPS limits how
many transactions may wait for inclusion at once, across all instances:

- **Pending-work limit.** Budget × lifetime / 4 transactions can be renewed in
  time (37,500 at the defaults), minus the transactions a reorganization of
  `OPS_NODE_POLICY_MAX_REORG_DEPTH` blocks (2 by default) could return to
  pending: that depth times the most transactions a block can hold
  (`OPS_NODE_POLICY_BLOCK_GAS_LIMIT` / 21,000; 200,000,000 gas by default).
  At the defaults the limit is 18,454. A new transaction above it is answered
  with 503, `Retry-After: 1` and the reason `pending_limit`.
- **Per-principal and per-organization limits**
  (`OPS_NODE_POLICY_PRINCIPAL_PENDING_LIMIT`,
  `OPS_NODE_POLICY_ORG_PENDING_LIMIT`). By default each is the pending-work
  limit minus the room everyone else keeps:
  2 × `OPS_NODE_POLICY_EXPECTED_TPS` × `OPS_NODE_POLICY_INCLUSION_BOUND`
  (2 × 2,000 × 1.5 s = 6,000), so 12,454 at the defaults. One principal, or
  all principals of one organization together, can carry the expected rate
  but can never take the others' room. Two organizations together can fill
  the pending-work limit; lower the limits for a deployment with many
  tenants. A new transaction above a limit is answered with 429,
  `Retry-After: 1` and the reason `principal_pending_limit` or
  `org_pending_limit`; other principals and organizations are still
  admitted.

Only transactions waiting for inclusion count. Included, stopped and final
ones do not, and resending a transaction OPS already recorded is never refused
for either limit. A reorganization can return transactions to pending above
the limit; nothing admitted is dropped, and new transactions wait until the
work drains.

| Variable | Default | Meaning |
|---|---|---|
| `OPS_NODE_POLICY_TRANSACTION_IDENTITY_TTL` | 300s | transaction identity lifetime (120 to 600 seconds) |
| `OPS_NODE_POLICY_MAX_AGE` | 10m | how long after submission OPS renews (at least the lifetime, at most 60 minutes) |
| `OPS_NODE_POLICY_RENEWAL_BUDGET` | 500 | renewals per second (1 to 2,000) |
| `OPS_NODE_POLICY_MAX_REORG_DEPTH` | 2 | deepest reorganization the limit leaves room for (0 to 64 blocks) |
| `OPS_NODE_POLICY_BLOCK_GAS_LIMIT` | 200000000 | the chain's block gas limit |
| `OPS_NODE_POLICY_EXPECTED_TPS` | 2000 | the transaction rate the deployment must sustain (same meaning as the node's setting) |
| `OPS_NODE_POLICY_INCLUSION_BOUND` | 1.5s | how long a transaction normally waits for its block (100 ms to 60 s) |
| `OPS_NODE_POLICY_PRINCIPAL_PENDING_LIMIT` | derived | per-principal limit (1 to the pending-work limit) |
| `OPS_NODE_POLICY_ORG_PENDING_LIMIT` | derived | per-organization limit (1 to the pending-work limit) |

OPS refuses to start when the numbers do not fit: when the pending-work limit
is not positive or is below the room the expected rate needs, or when the
derived per-principal or per-organization limit is below what one tenant
needs at the expected rate. A shorter identity lifetime needs a proportionally larger budget (at
120 seconds, about 935 renewals per second at the other defaults). OPS logs
the derived limits at startup. Up to 16 renewal re-checks run at once, so a
budget is met only while one re-check takes less than 16 / budget seconds;
OPS logs a warning when re-checks fall behind it. Size the node's pending
capacity (`OPS_NODE_POLICY_PENDING_LIMIT` on the node) for at least budget ×
lifetime / 4; the node adds the transactions waiting for finality itself.

If renewals still fall behind (OPS overloaded, a slow re-check), an identity
can lapse: the transaction stays `pending`, cannot execute and holds back the
sender's later nonces until the renewal lands. Nothing is lost.

Every renewal first runs the whole admission check again on current data: the
principal (deleted, banned, KYC), the organization and the membership, the
method and the target contract, the linked signer, the read profile's
`visibleTo` rule and compliance. Compliance re-evaluates every rule but accepts
only the travel-rule record already bound to this transaction and never claims
another one. A refusal stops renewal with that reason (`renewal_stopped`, not
final); an infrastructure error is retried and decides nothing. A renewed
identity carries the current fact version, so a revocation committed before the
renewal always applies. OPS renews for at most `OPS_NODE_POLICY_MAX_AGE`
(default 10 minutes, at least the transaction identity lifetime, at most 60
minutes) after the transaction was submitted; after that it reports
`renewal_stopped` with the reason `max_age`.

The node itself enforces bans, KYC, memberships, linked signers, contract
access and sanctions on current facts at execution. Checks that only OPS
performs — the method allowlist, compliance and the read profile's `visibleTo`
rule — are re-run at each renewal, so a change to them reaches a transaction
that is already pending within one transaction identity lifetime (five minutes
by default); a shorter `OPS_NODE_POLICY_TRANSACTION_IDENTITY_TTL` narrows that
window.

Renewals are sent only to a ready node, on the connection pool for outcome
checks (`OPS_NODE_POLICY_RECOVERY_CONNS`). After a two-minute node outage, the
pending transactions are renewed within the budget and included without any
client action; a principal revoked meanwhile is not renewed, and its
transactions never execute.

Each renewal is an automated re-authorization performed by OPS on behalf of the
original principal. It is recorded in the audit access log before it takes
effect (as `ops.system.recovery`, or `ops.system.identity_renewal` for an
expiring identity) with the principal, the organization, the transaction and
the reason; refusals, stops and `dropped` decisions are recorded the same way
(`ops.system.renewal_refused`, `ops.system.renewal_stopped`,
`ops.system.dropped`). Without the durable audit buffer (`AUDIT_BUFFER_DIR`),
OPS takes none of these decisions.

If the execution-tracking database is lost or recreated, transactions in
flight at that moment lose their OPS follow-up: a deployment that finalizes
afterwards is not registered automatically. A named human with full authority
over the deploying organization can register it from the node's finalized
evidence with `POST /api/v1/admin/orgs/{org_id}/execution/ownership-recovery`
(`{"transactionHash": "0x…"}`), within the node's evidence retention
(`OPS_NODE_POLICY_MANIFEST_RETENTION` on the node). It applies at most once per
transaction, never registers an address another organization owns, and is
recorded in the RBAC audit log. Any transaction that is unknown, not final, not
a deployment or not that organization's answers the same 404.

To decide `dropped` and to notice a transaction the node's pool lost, OPS
asks the private endpoint, which reports at its own finalized block whether a
block holds the transaction and the sender's nonce. With a node that does not
offer that answer, OPS reads the node's public RPC (`NODE_URL`) instead: then
point it at the same single node as the private endpoint, not at a
load-balanced pool of nodes. OPS records `dropped` only after the same
evidence was read twice, at least 30 seconds apart; a lookup the node could
not answer is never evidence.
